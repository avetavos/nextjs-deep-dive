## The idea in one sentence

A mutation is a four-step flow: validate the input, write to the database, call `updateTag`, `revalidateTag`, or `revalidatePath` to refresh the affected cached data, and optionally `redirect` — so the UI reflects the change without a manual reload.

## The full mutation flow

Inside the action you validate first, then mutate, then revalidate the data that just changed. Only after revalidation do you redirect, because `redirect` throws internally and stops the rest of the function from running.

```ts
// app/actions.ts — validate, write, revalidate, redirect
'use server'

import { revalidatePath } from 'next/cache'
import { redirect } from 'next/navigation'
import { z } from 'zod'

const schema = z.object({ title: z.string().min(1) })

export async function createPost(formData: FormData) {
  const parsed = schema.safeParse({ title: formData.get('title') })
  if (!parsed.success) {
    return { error: 'Invalid title' }
  }

  await db.post.create({ data: { title: parsed.data.title } })

  revalidatePath('/posts')
  redirect('/posts')
}
```

## updateTag, revalidateTag, and revalidatePath

`revalidatePath('/posts')` invalidates everything cached for that route. Tag-based invalidation is more surgical when the same data appears on several routes: tag your reads, then expire the tag after the write. Inside a Server Action use `updateTag('posts')` — it expires the tag immediately, so the very next request waits for fresh data and the user reads their own write. `revalidateTag(tag, profile)` instead marks the tag stale and keeps serving the old data while it refreshes in the background; in Next.js 16 the second `profile` argument is required (the one-argument form is deprecated and a TypeScript error) and `'max'` is the recommended value. Reach for `revalidateTag` in Route Handlers and webhooks, where `updateTag` is not allowed.

```ts
// app/posts/data.ts — tag the read so you can revalidate by tag later
export async function getPosts() {
  const res = await fetch('https://api.example.com/posts', {
    next: { tags: ['posts'] },
  })
  return res.json()
}
```

```ts
// app/actions.ts — expire only the tagged data so the next request sees the write
'use server'

import { updateTag } from 'next/cache'

export async function publishPost(id: string) {
  await db.post.update({ where: { id }, data: { published: true } })
  updateTag('posts')
}
```

```ts
// app/api/revalidate/route.ts — outside a Server Action, use revalidateTag with a profile
import { revalidateTag } from 'next/cache'

export async function POST() {
  revalidateTag('posts', 'max')
  return Response.json({ revalidated: true })
}
```

## How the client caches get refreshed

This ties back to the caching module. On the server, revalidation clears the Data Cache entry for the affected fetch. On the client, the Server Action response also refreshes the Client Cache for the current route, so the already-rendered segments are replaced with fresh server output. The user sees the new data without a hard reload — the two caches stay consistent.
