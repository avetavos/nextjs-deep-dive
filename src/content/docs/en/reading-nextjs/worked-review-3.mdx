## The feature

The prompt was: *"Build a product catalog with a grid, individual product pages, and an Add to cart button."* This is a `cacheComponents: true` project too, and the product pages are meant to be prerendered at build time — a real e-commerce catalog can't afford a server round trip per visitor for pages that barely change. Read it in the same [reading order](/nextjs/en/reading-nextjs/index/) as the first two reviews: boundaries first, then routing, then the caching model, then the optimization details a shopping site lives or dies by. It has **6 real bugs**, and `next build` catches four of them outright.

## The review walk

### Boundaries: `ssr: false` passed to `next/dynamic` inside a Server Component

`recently-viewed.tsx` has no `'use client'` directive — it's a Server Component — and it calls `dynamic(() => import(...), { ssr: false })`.

<SpotTheBug code={`import dynamic from 'next/dynamic'

const RecentlyViewedWidget = dynamic(() => import('./recently-viewed-widget'), { ssr: false })

export function RecentlyViewed() {
  return <RecentlyViewedWidget />
}`}>
`ssr: false` means "never render this on the server at all" — a request that only a Client Component can make about itself, since a Server Component has no client-side equivalent to fall back to. Building this exact file fails immediately:

```text
Error: Turbopack build failed with 1 error:
./app/products/[id]/recently-viewed.tsx:4:20
Error: `ssr: false` is not allowed with `next/dynamic` in Server Components. Please move it into a Client Component.
```

The fix Next.js's own error message names is the right one: add `'use client'` to the top of this file. `next/dynamic`'s `ssr: false` option is then a request the framework can actually honor, since the whole module is already client-only.
</SpotTheBug>

### Routing: a plain `<a>` for an internal route

The product grid links to each product page with `<a href={...}>` instead of `<Link>`.

<SpotTheBug code={`<a key={p.id} href={\`/products/\${p.id}\`}>
  <div style={{ position: 'relative', height: 200 }}>
    <Image src={p.image} alt={p.name} fill style={{ objectFit: 'cover' }} />
  </div>
  <p>{p.name}</p>
</a>`}>
A plain `<a>` still navigates — that's exactly why this bug is easy to miss in a quick look. Built and clicked in a real browser, the difference shows up in the network log, not in whether the page works. Clicking a `<Link href="/products/1">` on the same page produces two small requests carrying an `_rsc` query parameter and nothing else:

```text
GET /products/1?_rsc=rq0KtoLEX-G_daAz -> 200
GET /products/1?_rsc=Uj6tDUbDhWjKIlIB -> 200
```

Clicking the plain `<a href="/products/2">` instead produces a full document request with no `_rsc` parameter at all, followed by every static asset — fonts, CSS, every JS chunk — downloading again from scratch, exactly like the very first page load:

```text
GET /products/2 -> 200   (a full navigation, not an RSC fetch)
GET /_next/static/media/797e433ab948586e-s.p.0r6juujl39pe6.woff2 -> 200
GET /_next/static/chunks/3n8-9sbopjxwd.css -> 200
GET /_next/static/chunks/3s6nzrbk-8mnv.js -> 200
... (every other static chunk, re-downloaded)
```

The fix is `<Link href={...}>` from `next/link` — visually and functionally identical for a user who never opens the network panel, but it skips the full-page reload and the re-download of every asset the browser already has.
</SpotTheBug>

### Caching model: an empty `generateStaticParams`

`generateStaticParams` on the product page returns `[]`.

<SpotTheBug code={`export async function generateStaticParams() {
  return []
}`}>
Under Cache Components, an empty `generateStaticParams` isn't just "no pages get prerendered" — it's a hard build error, because the framework can no longer perform its build-time validation that nothing dynamic leaks through for a param set it never sees:

```text
Error: When using Cache Components, all `generateStaticParams` functions must return at least one result. This is to ensure that we can perform build-time validation that there is no other dynamic accesses that would cause a runtime error.

Learn more: https://nextjs.org/docs/messages/empty-generate-static-params
```

The fix is to actually return the real param set — `listProducts()` already exists in this exact codebase for the grid page; `generateStaticParams` just needs to map it to `{ id }` objects, exactly as the [static and dynamic rendering](/nextjs/en/rendering/static-and-dynamic-rendering/) lesson shows for the general case.
</SpotTheBug>

### Caching model: `export const runtime = 'edge'` next to `cacheComponents`

The product page also exports `runtime = 'edge'`.

<SpotTheBug code={`export const runtime = 'edge'`}>
This is the same category of failure the [route segment config](/nextjs/en/rendering/route-segment-config-and-runtimes/) lesson proves for every Route Segment Config export — `runtime` is rejected under Cache Components for *either* value, not just `'edge'`, because Cache Components requires the Node.js runtime and there's nothing left to configure:

```text
Error: Turbopack build failed with 1 error:
./app/r3b5/page.tsx:2:14
Error: Route segment config "runtime" is not compatible with `nextConfig.cacheComponents`. Please remove it.
```

The fix is simply to delete the export. There's no replacement needed — the default Node.js runtime is the only one Cache Components supports.
</SpotTheBug>

### Optimization: `next/image` with `fill` and no `sizes`

Both the grid thumbnails and the product-detail image use `fill` with no `sizes` prop.

<SpotTheBug code={`<div style={{ position: 'relative', width: 400, height: 400 }}>
  <Image src={product.image} alt={product.name} fill style={{ objectFit: 'cover' }} />
</div>`}>
With no `sizes` prop, Next.js defaults `fill` images to `sizes="100vw"` — the browser is told the image is as wide as the viewport, no matter how small the box actually is. Building the grid page and reading the rendered HTML shows exactly what that costs: with a 300px-wide grid cell and no `sizes`, the browser picks a **640px-wide** candidate — the smallest one that "covers" a full 400px viewport under the `100vw` assumption:

```text
sizes="100vw"
srcSet="/_next/image?url=%2Fproduct.png&w=640&q=75 640w, ... up to ... &w=3840&q=75 3840w"
```

The fix is a `sizes` value that matches the actual rendered width: `sizes="(max-width: 768px) 100vw, 33vw"` for the roughly-one-third-width grid cells, and a fixed `sizes="400px"` for the single, fixed-size product-detail image. Built with the fix in place, the product-detail page's image correctly requests the 400px candidate instead of the largest one in the `deviceSizes` list.
</SpotTheBug>

### Optimization: `viewport` inside `metadata`

`generateMetadata` sets `viewport` as a field on the returned `Metadata` object.

<SpotTheBug code={`export async function generateMetadata({
  params,
}: {
  params: Promise<{ id: string }>
}): Promise<Metadata> {
  const { id } = await params
  const product = await getProduct(id)
  return {
    title: product?.name ?? 'Product',
    viewport: 'width=device-width, initial-scale=1',
    openGraph: { images: [product?.image ?? '/product.png'] },
  }
}`}>
`viewport` used to be a field on `metadata` in older Next.js versions; today it's its own export (`viewport` or `generateViewport`). Putting it inside `metadata` doesn't error — it just gets dropped, with a warning that's easy to miss in a long build log:

```text
⚠ Unsupported metadata viewport is configured in metadata export in /r3b3. Please move it to viewport export instead.
Read more: https://nextjs.org/docs/app/api-reference/functions/generate-viewport
```

Every visitor on a phone gets the browser's default (usually non-responsive) viewport behavior instead of the one this code was clearly trying to set. The fix is a sibling `export const viewport: Viewport = { width: 'device-width', initialScale: 1 }` in the root layout — set once, it applies to every page, including this one.
</SpotTheBug>

## What changed and why

| # | Bug | Category | Fix |
|---|---|---|---|
| 1 | `dynamic(..., { ssr: false })` inside a Server Component | Boundaries | Add `'use client'` to the file that calls `dynamic()` |
| 2 | `<a href={...}>` for an internal route | Routing | `<Link href={...}>` from `next/link` |
| 3 | `generateStaticParams` returned `[]` | Caching model | Return the real param set from `listProducts()` |
| 4 | `export const runtime = 'edge'` next to `cacheComponents` | Caching model | Delete the export — Node.js is the only supported runtime |
| 5 | `next/image` with `fill` and no `sizes` | Optimization | A `sizes` value matching the actual rendered width |
| 6 | `viewport` as a field inside `metadata` | Optimization | A separate `export const viewport: Viewport` |

## Mental Model

Four of this review's six bugs are build-time facts that `next build` already refuses outright — `ssr: false` in a Server Component, an empty `generateStaticParams`, and `runtime` under Cache Components all fail loudly, in the same build. The other two — a plain `<a>` and a missing `sizes` — build completely clean and only cost something real once a visitor's browser actually loads the page: a full page reload instead of an instant client navigation, and several times more image data than the layout needed. Neither shows up by reading the JSX; both show up in the network panel.

## Common Misconceptions

- **"`ssr: false` is just a performance hint that any component can use."** It's a request only a Client Component can make about itself — a Server Component has no client fallback to opt out *to*.
- **"An empty `generateStaticParams` just means `next build` skips prerendering, same as always."** Under Cache Components specifically, it's a hard build error, not a silent no-op — the framework needs at least one param to validate against.
- **"A plain `<a>` for an internal link still works, so it's not really a bug."** It navigates correctly, which is exactly why it survives code review — the cost only shows up in the network panel as a full reload and a re-download of every static asset.
