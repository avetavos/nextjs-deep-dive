## The idea in one sentence

Cache Components flips the model: instead of remembering per-`fetch` cache options, you mark a function, file, or component with the `'use cache'` directive to say **"cache this,"** then shape its lifetime and invalidation with `cacheLife` and `cacheTag`.

## The `use cache` directive

Add the string `'use cache'` at the top of a function (or file) and everything it returns is cached — a `fetch`, a database query, or a whole rendered component. It replaces scattering `cache` options across individual calls.

```tsx
// lib/data.ts
import { cacheLife, cacheTag } from 'next/cache'

async function getData() {
  'use cache'
  cacheLife('hours')
  cacheTag('data')
  const res = await fetch('https://api.example.com/data')
  return res.json()
}
```

## cacheLife and cacheTag

`cacheLife` sets how long the entry stays fresh — a named profile like `'hours'` or an explicit object. `cacheTag` attaches a tag so you can invalidate it on demand: `revalidateTag(tag, 'max')` marks it stale and serves the old entry while refreshing (in Next.js 16 the second argument is required — the one-argument form is deprecated and a TypeScript error), and inside a Server Action `updateTag(tag)` expires it immediately so the user reads their own write.

```tsx
import { cacheLife, cacheTag } from 'next/cache'

async function getProduct(id: string) {
  'use cache'
  cacheTag(`product-${id}`)
  cacheLife({ stale: 60, revalidate: 300 })
  return db.product.findUnique({ where: { id } })
}
```

## Turning it on: cacheComponents and Partial Prerendering

`'use cache'` requires the `cacheComponents` flag. In Next.js 16 that same flag is **also** how you opt into **Partial Prerendering** — the older experimental `ppr` flag and `experimental_ppr` export were removed. With it on, Next.js prerenders a static shell and streams the dynamic, uncached holes in at request time.

```ts
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig
```

## Private and remote caches

Two variants extend the model, both shipped with Cache Components in Next.js 16. `'use cache: private'` may read `cookies()`, `headers()`, and `searchParams` directly; its result is never written to a shared server cache — it is kept **per browser**, in the client's memory for the `stale` window, so it is never shared across visitors. `'use cache: remote'` stores the entry in a shared, durable cache handler (Redis, KV, or whatever the platform provides via `cacheHandlers`) so every server instance and every user hits the same entry, at the cost of a network round trip.

```tsx
import { cacheLife } from 'next/cache'
import { cookies } from 'next/headers'

async function getRecommendations() {
  'use cache: private'
  cacheLife({ stale: 60 })
  const sessionId = (await cookies()).get('session-id')?.value
  return db.recommendations.forSession(sessionId)
}
```
