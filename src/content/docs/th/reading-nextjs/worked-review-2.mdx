## ฟีเจอร์นี้คืออะไร

โจทย์ที่ให้ AI คือ: *"สร้างแดชบอร์ดที่อยู่หลัง login มีกราฟแบบ stream และฟอร์มตั้งค่าที่ผู้ใช้ save ได้"* โปรเจกต์นี้เปิด `cacheComponents: true` ใน `next.config.ts` อยู่แล้ว — AI assistant รู้เรื่องนี้และเขียนโค้ดส่วนใหญ่ให้เข้ากับมัน แต่ก็ยังหยิบบางรูปแบบมาจากข้อมูลฝึกก่อนเวอร์ชัน 16 อยู่ดี อ่านตาม[ลำดับการอ่าน](/nextjs/th/reading-nextjs/index/)เดียวกับรีวิวแรก: boundary กับ rendering ก่อน แล้วค่อย caching model แล้วค่อย config โค้ดชุดนี้มี **bug จริง 6 จุด** และ `next build` จับได้แค่ 2 จุดเท่านั้น

## เดินรีวิวทีละจุด

### Boundary/rendering: `Date.now()` ถูกอ่านตรงๆ ใน render ของ Client Component

`LastRefreshed` พิมพ์ `Date.now()` ลงไปใน JSX ตรงๆ

<SpotTheBug code={`'use client'

export function LastRefreshed() {
  return <p>Last refreshed: {Date.now()}</p>
}`}>
Client Component ทุกตัว render สองครั้ง: ครั้งแรกบนเซิร์ฟเวอร์สำหรับ HTML เริ่มต้น ครั้งที่สองใน browser ตอน hydration `Date.now()` มีความละเอียดระดับมิลลิวินาที ดังนั้นสอง render นี้แทบจะไม่มีทางตรงกัน โหลดคอมโพเนนต์นี้จริงใน browser กับ `next dev` จะเกิด hydration-mismatch error ของ React 19 เอง พร้อมค่าทั้งสองตัวที่ไม่ตรงกันจริง:

```text
Error: Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client. This can happen if a SSR-ed Client Component used:

- A server/client branch `if (typeof window !== 'undefined')`.
- Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
- Date formatting in a user's locale which doesn't match the server.
- External changing data without sending a snapshot of it along with the HTML.
- Invalid HTML tag nesting.

...
  <Page params={Promise} searchParams={Promise}>
    <p>
+                           1790318503755
-                           1790318503711
```

วิธีแก้เหมือนที่บท[static และ dynamic rendering](/nextjs/th/rendering/static-and-dynamic-rendering/)พิสูจน์ไว้: ใช้ `useSyncExternalStore` กับ `getServerSnapshot` ที่ตายตัว เพื่อให้ render บน server กับ render ตอน hydration เห็นค่า placeholder ตรงกันโดยโครงสร้าง แล้วค่อยแสดงเวลาจริงหลังจาก hydration เสร็จ
</SpotTheBug>

### Boundary/rendering: `useFormState` แทนที่จะเป็น `useActionState`

`SettingsForm` import `useFormState` จาก `react-dom`

<SpotTheBug code={`'use client'

import { useFormState } from 'react-dom'
import { saveSettings } from './actions'

export function SettingsForm() {
  const [state, formAction] = useFormState(saveSettings, { ok: false, name: '' })
  return (
    <form action={formAction}>
      <input name="name" defaultValue={state.name} />
      <button type="submit">Save</button>
      {state.ok && state.name && <p>Saved {state.name}</p>}
    </form>
  )
}`}>
`useFormState` เป็นชื่อเดิมสมัย React 18 canary React 19 เปลี่ยนชื่อเป็น `useActionState` แล้วย้ายไปอยู่ที่ package `react` `react-dom` ยังคง export `useFormState` ไว้เพื่อความเข้ากันได้ย้อนหลัง แต่มัน log console error จริง โดยระบุชื่อคอมโพเนนต์ตรงๆ ทันทีที่รัน — บันทึกไว้เป๊ะๆ กับ React 19.2.8 ใน browser จริง:

```text
[ERROR] ReactDOM.useFormState has been renamed to React.useActionState. Please update %s to use React.useActionState. SettingsForm
```

build ผ่านทั้งสองแบบ — นี่เป็นสัญญาณ runtime เท่านั้น ที่ `next build` และ `tsc` มองไม่เห็น วิธีแก้คือ `import { useActionState } from 'react'` แทนที่ `useFormState` จาก `react-dom` โดย signature การเรียกไม่เปลี่ยน
</SpotTheBug>

### Caching model: `cookies()` ถูกอ่านเหนือ boundary ของ `<Suspense>`

`next.config.ts` เปิด `cacheComponents: true` ไว้ `DashboardPage` อ่าน `cookies()` ที่บนสุดของฟังก์ชัน ก่อนจะ return JSX ใดๆ เลย — รวมถึง boundary `<Suspense>` รอบ `Chart` ด้วย

<SpotTheBug code={`import { cookies } from 'next/headers'
import { Suspense } from 'react'
import { Chart } from './chart'

export default async function DashboardPage() {
  const theme = (await cookies()).get('theme')?.value ?? 'light'
  return (
    <main>
      <p>theme: {theme}</p>
      <Suspense fallback={<p>Loading chart…</p>}>
        <Chart />
      </Suspense>
    </main>
  )
}`}>
ภายใต้ Cache Components request-time API ต้องอยู่ข้างใน boundary `<Suspense>` — framework ต้องรู้แน่ชัดว่าส่วนไหนของ tree ที่ได้รับอนุญาตให้รอ request data เพื่อจะ prerender ส่วนที่เหลือเป็น static shell ได้ `cookies()` ตรงนี้รันก่อนที่ฟังก์ชันจะ return JSX ใดๆ เลย เลยยังไม่มี boundary ล้อมมันอยู่ build หน้านี้จริงล้มเหลวทันที ไม่ใช่แค่ warning ลอยๆ:

```text
Error: Route "/dashboard": Next.js encountered uncached or runtime data during prerendering.

`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>` prevents the route from being prerendered, blocking the page load and leading to a slower user experience.

Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"` (does not apply to `connection()`)
  - [block] Set `export const instant = false` to allow a blocking route
```

วิธีแก้คือย้ายการอ่าน `cookies()` ลงไปเป็นคอมโพเนนต์ async เล็กๆ ของตัวเอง แล้วห่อด้วย `<Suspense>` ของตัวเอง เหมือนกับที่ `await` ที่ช้าได้ boundary ของตัวเองในบท[streaming และ Suspense](/nextjs/th/rendering/streaming-and-suspense/)
</SpotTheBug>

### Caching model: route segment config export อยู่ข้างๆ `cacheComponents`

`app/dashboard/page.tsx` ยังมี `export const revalidate = 60` อยู่บนสุดของไฟล์ด้วย

<SpotTheBug code={`export const revalidate = 60

export default async function DashboardPage() {
  // ...
}`}>
Route Segment Config (`dynamic`, `revalidate`, `fetchCache`, `dynamicParams`, `runtime`) คือ caching model *แบบเก่า* มันขัดแย้งกับ Cache Components โดยตรง — export เหล่านี้ทุกตัวทำให้ build ล้มเหลวทันทีที่ `cacheComponents: true` ถูกตั้งไว้ ไม่ว่าค่าจะเป็นอะไรก็ตาม:

```text
Error: Turbopack build failed with 1 error:
./app/dashboard/page.tsx:2:14
Error: Route segment config "revalidate" is not compatible with `nextConfig.cacheComponents`. Please remove it.
```

ไม่มีตัวแทนตรงๆ สำหรับ `revalidate` ระดับหน้าเว็บภายใต้ Cache Components — สิ่งที่เทียบเท่าคือห่อส่วนงานที่ต้อง cache จริงๆ ด้วย `'use cache'` พร้อม profile `cacheLife` ในระดับที่ต้องการจริงๆ ตามที่ตารางเทียบเต็มรูปแบบในบท[route segment config](/nextjs/th/rendering/route-segment-config-and-runtimes/)แสดงไว้
</SpotTheBug>

### Config: `middleware.ts` ที่สมมติว่าใช้ Edge runtime

โปรเจกต์นี้มี `middleware.ts` (ไม่ใช่ `proxy.ts`) ที่อ่าน `randomUUID` จาก `node:crypto` และเปิดใช้ Edge runtime

<SpotTheBug code={`import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
import { randomUUID } from 'node:crypto'

export const config = { runtime: 'edge' }

export function middleware(request: NextRequest) {
  const requestId = randomUUID()
  const response = NextResponse.next()
  response.headers.set('x-request-id', requestId)
  return response
}`}>
มีสัญญาณจริงสามอย่างแยกกันเกิดขึ้นกับไฟล์นี้ ตามลำดับ อย่างแรกคือชื่อไฟล์เอง:

```text
⚠ The "middleware" file convention is deprecated. Please use "proxy" instead.

  To migrate automatically, run:
  npx @next/codemod@canary middleware-to-proxy .
```

อย่างที่สอง Edge runtime โหลด built-in ของ Node.js ไม่ได้จริงๆ:

```text
Warning: A Node.js module is loaded ('node:crypto' at line 3) which is not supported in the Edge Runtime.
```

อย่างที่สาม build ล้มเหลวทันที เพราะ Edge เองถูก deprecate สำหรับการ render แล้ว:

```text
Error: Page /middleware provided runtime 'edge', the edge runtime for rendering is currently experimental. Use runtime 'experimental-edge' instead.
```

วิธีแก้คือเปลี่ยนชื่อไฟล์พร้อมเอา runtime opt-in และ Node-only import ออกทั้งคู่: `proxy.ts`, ไม่มี `config.runtime`, และ `NextResponse.next()` เฉยๆ ก็เพียงพอสำหรับ proxy ที่ forward header — runtime ค่า default (และตอนนี้เป็นตัวเดียวที่สมเหตุสมผล) คือ Node.js ตามที่บท[proxy และ request lifecycle](/nextjs/th/production-and-ecosystem/middleware-and-the-request-lifecycle/)กำหนดไว้
</SpotTheBug>

### Config: secret จริงซ่อนอยู่หลัง `NEXT_PUBLIC_`

`AnalyticsWidget` อ่าน `process.env.NEXT_PUBLIC_ANALYTICS_KEY` — ชื่อที่ฟังดูเหมือน analytics id สาธารณะที่บทอื่นๆ ในคอร์สนี้ใช้เป็นตัวอย่าง แต่ตรงนี้มันเก็บ API key ที่ใช้งานจริงอยู่

<SpotTheBug code={`'use client'

export function AnalyticsWidget() {
  return <div data-analytics-id={process.env.NEXT_PUBLIC_ANALYTICS_KEY} />
}`}>
prefix `NEXT_PUBLIC_` ทำตามที่มันบอกไว้เป๊ะๆ ไม่ว่าตัวแปรจะชื่ออะไรจริงๆ — มันบอก Next.js ให้ inline ค่านั้นแบบ literal ลงใน JavaScript ที่ส่งไปให้ผู้เยี่ยมชมทุกคน ตั้งค่า `NEXT_PUBLIC_ANALYTICS_KEY` เป็น secret ที่ดูเหมือนใช้งานจริงใน `.env.local` แล้ว build คอมโพเนนต์นี้เป๊ะๆ จากนั้น grep chunk ของ client ที่ build ออกมา จะเจอค่านั้นอยู่เป็นข้อความธรรมดา:

```text
["default",0,function(){return(0,e.jsx)("div",{"data-key":"sk_live_51H8xNOTAREALSE...
```

ไม่มีอะไรตรงนี้เป็น build error หรือแม้แต่ warning เลย — ค่า `NEXT_PUBLIC_` ถูกออกแบบมาให้ inline อยู่แล้ว และ Next.js ไม่มีทางรู้ว่าตัวนี้เป็น credential จริงไม่ใช่ id สาธารณะธรรมดา วิธีแก้คือห้ามใส่ prefix ให้ค่าที่ต้องเก็บเป็นความลับเด็ดขาด API key จริงควรอยู่ในตัวแปรที่ไม่มี prefix และเป็น server-only (`ANALYTICS_SECRET_KEY`) อ่านได้เฉพาะข้างใน Server Component, Server Action, หรือ Route Handler เท่านั้น ตามที่บท[environment และ configuration](/nextjs/th/production-and-ecosystem/environment-and-configuration/)พิสูจน์ไว้สำหรับกรณีกลับกัน (ค่าที่สาธารณะจริงๆ แต่ถูกเข้าถึงผิดวิธี)
</SpotTheBug>

## Mental Model

Bug ในรีวิวนี้แบ่งออกเป็นสองแบบชัดเจน และการแบ่งนี้ตรงกับสิ่งที่เครื่องมือมองเห็นได้พอดี `cookies()` เหนือ `<Suspense>` กับ bug segment-config-ข้างๆ-`cacheComponents` ทั้งสองอันเป็นข้อเท็จจริงตอน build — `next build` รู้อยู่แล้วว่าโปรเจกต์นี้ใช้ caching model แบบไหนและปฏิเสธโค้ดที่เขียนสำหรับอีกแบบหนึ่ง ส่วน `Date.now()` ใน render, `useFormState`, การสมมติว่าใช้ Edge runtime, และ secret ที่รั่วไหล ล้วนเป็นข้อเท็จจริงตอน runtime — โค้ดถูกต้องตามไวยากรณ์ Next.js ทั้งคู่แบบ และมีแค่การรันจริงเท่านั้น — browser จริง, request จริง, grep ผ่านผลลัพธ์ที่ build ออกมาจริง — ที่จะบอกได้ว่าเจอแบบไหนอยู่

## ความเข้าใจผิดที่พบบ่อย

- **"`cacheComponents: true` ใน `next.config.ts` แปลว่าทุกไฟล์ในโปรเจกต์เขียนมาสำหรับมันอยู่แล้ว"** โปรเจกต์นี้เปิด flag ไว้แล้วจริงๆ แต่ก็ยังมี route segment config export กับ `middleware.ts` ที่เขียนเหมือน tutorial ก่อนเวอร์ชัน 16 — flag ไม่ได้ย้อนกลับไปแก้โค้ดที่เขียนสำหรับ model เก่าให้อัตโนมัติ
- **"ชื่อตัวแปรอย่าง `NEXT_PUBLIC_ANALYTICS_KEY` ปลอดภัยเพราะฟังดู*เหมือน*กับ public id ที่ตัวอย่างอื่นใช้"** prefix จะ inline อะไรก็ตามที่ตัวแปรนั้นเก็บอยู่จริง ไม่ว่าชื่อที่เหลือจะสื่อความหมายว่าอะไรก็ตาม
- **"`useFormState` ยังใช้งานได้ แปลว่าไม่ใช่ bug จริง"** มันรันได้ แต่ React 19 log error จริงที่ระบุชื่อคอมโพเนนต์ที่ผิดพลาดตรงๆ — การมองว่า "ไม่ crash" แปลว่า "โอเคแล้ว" พลาดสัญญาณที่ framework พยายามบอกอยู่จริงๆ
