## ไอเดียในหนึ่งประโยค

Server Component เป็น `async` function จึง `await` `fetch` หรือ query database ได้ **ตรง ๆ** ในตัว component ไม่ต้องมี `useEffect` ไม่ต้องมี loading state และไม่ต้องยิงจาก client ไปหา API

## Fetch ตรง ๆ ใน async component

ใน App Router component รันบน server เรา fetch ตรงจุดที่ render และ data ไม่หลุดเข้า client bundle จนกว่าจะส่ง HTML ออกไป

```tsx
// app/products/page.tsx
function ProductList({ products }: { products: { id: string; name: string }[] }) {
  return (
    <ul>
      {products.map((p) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  )
}

export default async function ProductsPage() {
  // Runs on the server — the API key and response stay server-side
  const res = await fetch('https://api.example.com/products')
  const products = await res.json()
  return <ProductList products={products} />
}
```

เพราะ code รันบน server เราจึงคุย database หรือ ORM ได้ตรง ๆ ไม่ต้องมี API route คั่นกลาง

```ts
// lib/db.ts
export const db = {
  user: {
    findMany: async () => [] as { id: string; name: string }[],
    findUnique: async (_args: { where: { id: string } }) =>
      null as { id: string; name: string } | null,
  },
  post: {
    findMany: async () => [] as { id: string; title: string }[],
  },
}
```

```tsx
// app/users/page.tsx
import { db } from '@/lib/db'

function UserList({ users }: { users: { id: string; name: string }[] }) {
  return (
    <ul>
      {users.map((u) => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  )
}

export default async function UsersPage() {
  // Query the database straight from the Server Component
  const users = await db.user.findMany()
  return <UserList users={users} />
}
```

## Sequential vs. parallel เลี่ยง waterfall

ถ้า `await` request แรกแล้วค่อย `await` ตัวถัดไป ตัวที่สองจะเริ่มไม่ได้จนกว่าตัวแรกจะเสร็จ นั่นคือ **waterfall** เมื่อ request ไม่ได้ขึ้นต่อกัน ให้ยิงพร้อมกันด้วย `Promise.all`

```tsx
// app/dashboard/page.tsx
function Profile({
  user,
  posts,
}: {
  user: { id: string; name: string } | null
  posts: { id: string; title: string }[]
}) {
  return (
    <div>
      <p>{user?.name}</p>
      <ul>
        {posts.map((p) => (
          <li key={p.id}>{p.title}</li>
        ))}
      </ul>
    </div>
  )
}

async function getUser(id: string) {
  const res = await fetch(`https://api.example.com/users/${id}`)
  return res.json()
}

async function getPosts(id: string) {
  const res = await fetch(`https://api.example.com/users/${id}/posts`)
  return res.json()
}

export default async function Dashboard() {
  // Parallel: both requests fire at once, no waterfall
  const [user, posts] = await Promise.all([getUser('1'), getPosts('1')])
  return <Profile user={user} posts={posts} />
}
```

## Dedupe ด้วย Request Memoization และ React.cache()

ภายใน render pass เดียว Next.js ทำ memoize `fetch` ที่เหมือนกันให้อัตโนมัติ เรียก URL เดิมจากสาม component แต่ network เห็นแค่ request เดียว ส่วนงานที่ไม่ใช่ `fetch` เช่น query database ให้ห่อด้วย `cache()` ของ React เพื่อ dedupe แบบ per-request เหมือนกัน

```ts
// lib/user.ts
import { cache } from 'react'
import { db } from '@/lib/db'

// Called by many components in one render — the query runs once per request
export const getUser = cache(async (id: string) => {
  return db.user.findUnique({ where: { id } })
})
```

### ขอบเขตคือ render pass เดียว ไม่มากไปกว่านั้น

สองเรื่องเกี่ยวกับ Request Memoization ที่คนที่เคยเข้าใจว่า "Next.js cache fetch ให้" มักเข้าใจผิด ทั้งสองข้อไม่จริง:

1. มันไม่ persist ข้าม request — มันถูกจำกัดขอบเขตแค่ render pass เดียว แล้วถูกทิ้งทันทีที่ render นั้นจบ การเก็บ data ข้าม request คือหน้าที่ของ Data Cache (บทถัดไป) ไม่ใช่บทนี้
2. มันไม่ทำงานใน Route Handler เพราะ Route Handler ไม่ใช่ส่วนหนึ่งของ React component tree เอกสารที่ bundle มากับ probe ของ `fetch` พูดตรง ๆ ว่า "Memoization does not apply in Route Handlers, since they are not part of the React component tree"

เพื่อพิสูจน์ทั้งสองข้อ ห่อ fake ORM call ด้วย `cache()` แล้ว log ทุกครั้งที่มันรันจริง:

```ts
// lib/counter.ts
import { cache } from 'react'

export const getUser = cache(async (id: string) => {
  const token = Math.random().toString(36).slice(2, 8)
  console.log(`[getUser] executing for id=${id} — fresh call, token=${token}`)
  return { id, token }
})
```

```tsx
// app/memo-demo/page.tsx
import { getUser } from '@/lib/counter'

export const dynamic = 'force-dynamic'

async function Widget({ label }: { label: string }) {
  const user = await getUser('1')
  return (
    <p>
      {label}: token {user.token}
    </p>
  )
}

export default async function MemoDemoPage() {
  // Two separate Server Components calling the same cache()-wrapped
  // function with the same argument, in the same render pass.
  return (
    <div>
      <Widget label="A" />
      <Widget label="B" />
    </div>
  )
}
```

```ts
// app/api/memo-demo/route.ts
import { getUser } from '@/lib/counter'

export const dynamic = 'force-dynamic'

export async function GET() {
  const user = await getUser('1')
  return Response.json(user)
}
```

Build ด้วย `next build && next start` แล้วยิง 3 ครั้ง — หน้าเพจสองครั้ง แล้วค่อย Route Handler หนึ่งครั้ง — server log จะโชว์การรันจริงแค่ครั้งเดียวต่อ request แม้ว่าหน้าเพจจะ render `Widget` สองตัวที่เรียก `getUser('1')` ทั้งคู่:

```text

[getUser] executing for id=1 — fresh call, token=dacca3
[getUser] executing for id=1 — fresh call, token=fv739g
```

`Widget` สองตัวของ request แรกใช้การรันเดียวกัน (`jhr7n2`) — นั่นคือ dedupe request ที่สองไปหน้าเพจเดิมได้ token ใหม่เอี่ยม (`dacca3`) — ขอบเขตจาก render แรกหายไปแล้ว Route Handler ก็ได้ token ของตัวเอง (`fv739g`) — มันไม่เคยแชร์อะไรกับ render ของหน้าเพจเลย ตรงตามที่เอกสารบอกไว้เป๊ะ

## ส่ง Promise ให้ `use()` ใน Client Component

Server Component สามารถเริ่ม fetch แล้วส่ง **Promise ที่ยังไม่ resolve** ตรง ๆ ให้ Client Component แทนที่จะ `await` ก่อน Client Component จะแกะมันด้วย `use()` ของ React และ `<Suspense>` ที่ห่ออยู่จะโชว์ fallback จนกว่าจะ resolve วิธีนี้ stream static shell ออกไปทันที และปล่อยให้ data ที่ช้ามาทีหลัง โดยไม่ต้องมี `useEffect` fetch ฝั่ง client

```tsx
// app/comments/comments.tsx
'use client'
import { use } from 'react'

export function Comments({
  commentsPromise,
}: {
  commentsPromise: Promise<{ id: string; text: string }[]>
}) {
  // Unwraps the Promise on the client — suspends until it resolves
  const comments = use(commentsPromise)
  return (
    <ul>
      {comments.map((c) => (
        <li key={c.id}>{c.text}</li>
      ))}
    </ul>
  )
}
```

```tsx
// app/comments/page.tsx
import { Suspense } from 'react'
import { Comments } from './comments'

async function getComments() {
  const res = await fetch('https://api.example.com/comments')
  return res.json()
}

export default function CommentsPage() {
  // Don't await — pass the Promise straight down, unresolved
  const commentsPromise = getComments()
  return (
    <Suspense fallback={<p>Loading comments…</p>}>
      <Comments commentsPromise={commentsPromise} />
    </Suspense>
  )
}
```

นี่คือคนละเครื่องมือกับ client-side data library อย่าง SWR หรือ TanStack Query: `use(promise)` แกะค่าที่ *server เริ่ม fetch ไว้แล้ว* ครั้งเดียว สำหรับ render นี้ ส่วน SWR/TanStack รันทั้งหมดใน browser และมี client-side cache, revalidation, refetch-on-focus เป็นของตัวเอง ใช้พวกนั้นเมื่อ Client Component ต้อง fetch **ด้วยตัวเอง** แยกจาก render ของ Server Component (search-as-you-type, polling, mutate แล้ว refetch) — คอร์สนี้ไม่ได้สอนพวกนั้น

## จุดที่ไม่ควร fetch

Client Component ใช้ `await` ในตัวเองไม่ได้ และห้ามแตะ database ตรง ๆ ต้องเข้าถึง data ผ่าน **Route Handler** หรือ data library ที่รันบน server แทน

```tsx
// app/search/search-box.tsx
'use client'
import { useState } from 'react'

export function SearchBox() {
  const [results, setResults] = useState([])
  async function onSearch(q: string) {
    // Client components fetch through a Route Handler, never the DB
    const res = await fetch(`/api/search?q=${q}`)
    setResults(await res.json())
  }
  return <input onInput={(e) => onSearch(e.currentTarget.value)} />
}
```

## Mental Model

มอง async Server Component เป็น function ที่รันครั้งเดียวต่อ request บน server โดยไม่มี "data layer" แยกออกมาต่างหาก — ตัว `await` **คือ** data layer นั่นเอง Request Memoization คือความจำระยะสั้นของ function นั้น ทุกอย่างที่มัน (และทุกอย่างที่มันเรียก) `await` ระหว่างการรันครั้งนั้นจะถูกจำไว้จนจบการรัน แล้วถูกลืม Route Handler คือ function invocation คนละตัวที่มีความจำระยะสั้นของตัวเอง มันไม่เคยสืบทอดความจำของหน้าเพจเลย

## ข้อแลกเปลี่ยน

| สิ่งที่ได้ | ประโยชน์ | ต้นทุน |
|---|---|---|
| Fetch ตรงในตัว component | ไม่มี client round-trip ไม่ต้องจัดการ loading state | ทุก Server Component ที่ต้องการ data ต้องเป็น `async` เอง |
| `Promise.all` สำหรับ request ที่ไม่ขึ้นต่อกัน | ไม่มี waterfall ทั้งสอง request เริ่มพร้อมกัน | ต้องสังเกตให้ออกว่า request ไม่ได้ขึ้นต่อกันจริง ๆ |
| `React.cache()` สำหรับงานที่ไม่ใช่ `fetch` | หนึ่ง query ต่อ request ไม่ว่ากี่ component จะเรียก | dedupe แค่ตอน argument เท่ากันแบบ reference หรือเป็น primitive — object literal ที่สร้างใหม่ทุกครั้งทำให้มันพัง |
| ส่ง Promise ให้ `use()` | stream static shell ก่อน data ที่ช้าจะมาถึง | ต้องมี `<Suspense>` boundary และ Promise ต้องถูกสร้างใน Server Component ไม่ใช่ Client Component |

## ความเข้าใจผิดที่พบบ่อย

- **"Request Memoization cache data ของฉันข้าม request ได้"** — ไม่จริง มันอยู่แค่ใน render pass เดียวแล้วก็ตาย การเก็บ data ข้าม request คือหน้าที่ของ Data Cache ซึ่งเป็นบทถัดไป
- **"ถ้าเรียก cached function จาก Route Handler มันจะใช้ผลลัพธ์ที่ cache ไว้จากหน้าเพจ"** — ไม่จริง Route Handler ไม่ใช่ส่วนหนึ่งของ React component tree จึงไม่มีทางเข้าร่วม memoization scope ของ render ของ Server Component ได้เลย
- **"`React.cache()` dedupe ด้วยการเทียบ argument แบบ deep-equal"** — มันเทียบแบบเดียวกับ `Object.is` สอง call ที่มี object ที่โครงสร้างเหมือนกันแต่สร้างใหม่ทุกครั้งคือคนละ reference และไม่มีทาง dedupe กัน
- **"Client Component `await` data เองได้เหมือน Server Component"** — ไม่ได้ render function ของ Client Component เป็น `async` ไม่ได้ มันต้องรับ data ที่ resolve แล้วผ่าน prop หรือแกะ Promise ด้วย `use()` เท่านั้น

## อ่านโค้ดที่ AI เขียน

เมื่อ snippet ที่ generate มา fetch หรือ cache data ใน Server Component ให้เช็กสิ่งเหล่านี้ก่อนเชื่อมัน:

- ทุก fetch ที่ต้องการ dedupe รันอยู่ใน render tree เดียวกันหรือเปล่า — ไม่ใช่อยู่ใน Route Handler ที่มันเรียกเข้าไปเอง?
- ถ้า call ที่ไม่ใช่ `fetch` (ORM query, SDK call) ถูกห่อด้วย `cache()` argument ของมันเป็น primitive หรือเป็น object reference *เดียวกัน* ทุกครั้งหรือเปล่า — ไม่ใช่ object literal ที่สร้างใหม่ทุก call site?
- Client Component พยายาม `await` data ตรง ๆ ในตัวมันหรือเปล่า? แบบนั้น compile ไม่ผ่าน — data ต้องมาเป็น prop หรือผ่าน `use()` เท่านั้น
- component ที่ต้องการ data แบบ parallel ใช้ `Promise.all` จริงหรือเปล่า หรือแอบ `await` ทีละตัวเงียบ ๆ จนเกิด waterfall?
- ถ้ามีการส่ง Promise ให้ Client Component ไปใช้ `use()` มี `<Suspense>` boundary ห่ออยู่หรือเปล่า? ถ้าไม่มี ทั้ง tree จะ block แทนที่จะ stream
